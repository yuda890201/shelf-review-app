# 売場添削アプリ

コンビニ・小売店向けの売場添削アプリ。フェーズ1「意見出しモード」— チームで1枚の売場写真を見ながら、画像上にピンを打って良い点・悪い点をリアルタイムでブレストするツール。

## フェーズ設計

1. **(このリポジトリの実装対象)** 意見出しモード — 画像+ピン+コメントを構造化データとして蓄積する
2. (将来) 蓄積データを使った類似画像検索ベースの簡易添削
3. (将来) VLM(Claude等)にチームの陳列基準を注入した添削精度向上

## 技術スタック

- Next.js 16 (App Router, TypeScript, Tailwind CSS)
- Supabase (Postgres + Auth + Storage + Realtime)
- `@supabase/ssr` によるサーバー/クライアント両対応のSupabaseクライアント

## セットアップ

### 1. Supabaseプロジェクトを作成

[supabase.com](https://supabase.com) でプロジェクトを作成し、`Project Settings > API` から URL と anon key を取得します。

### 2. マイグレーションを適用

`supabase/migrations/` 配下のSQLをSupabase SQL Editor で順番に実行するか、Supabase CLIでリンクして適用します。

```bash
npx supabase link --project-ref <your-project-ref>
npx supabase db push
```

マイグレーション内容:

- `20250101000003_rls_policies.sql` — Row Level Security(ログイン済みユーザーは全件閲覧可、投稿は自分のuser_idのみ、セッションのクローズは司会者本人のみ)

- `20250101000005_profiles.sql` — 匿名ログインの表示名を保存する `profiles` テーブル
- `20250101000006_reactions.sql` — セッション(写真)単位の「ありがとう」「まだまだ」リアクション用 `reactions` テーブル
- `20250101000007_comment_frame_style.sql` — コメントピンの枠のサイズ・角度・色を保存するカラムを `comments` に追加
- `20250101000008_resolved_sessions.sql` — 「対応済み」フラグと改善後(after)写真用のカラムを `sessions` に追加
- `20250101000009_notifications_seen_at.sql` — 通知バッジ計算用に最終閲覧時刻を保存するカラムを `profiles` に追加

- `20250101000011_push_subscriptions.sql` — Web Push通知の購読情報を保存する `push_subscriptions` テーブルを追加(任意機能。設定しなくても他の機能には影響しません)
- `20250101000012_tags.sql` — コメント入力時の「よく使う文言」スタンプを独立管理する `tags` テーブルを追加(投稿から自動的に蓄積され、手動での追加・編集・削除も可能)
- `20250101000013_layouts.sql` — 本部レイアウト比較機能用の `layouts` / `layout_reference_photos` / `layout_current_photos` / `layout_tasks` テーブルを追加
- `20250101000014_pins.sql` — 本部レイアウト比較の写真(お手本・現在の売場のどちらか一方)に流れるコメントピンを打てる `pins` テーブルを追加
- `20250101000015_stores_and_trucks.sql` — それまでソースコードに直書きしていた店舗リスト・納品トラック(便)リストをテーブル化する `stores` / `delivery_trucks` を追加(既存の値を初期データとして投入済み)
- `20250101000016_pin_object_kind.sql` — `pins` にテキストなしのアイコンオブジェクト(移動/フェイス拡げる/フェイス縮める)を表せる `object_kind` カラムを追加
- `20250101000017_comment_object_kind.sql` — 日々の投稿のコメントピン(`comments`)にも同じ `object_kind` カラムを追加
- `20250101000018_pin_end_position.sql` — オブジェクトピンを「始点→終点」の線として描画するため、終点座標 `end_position_x` / `end_position_y` を `pins` / `comments` 両方に追加
- `20250101000019_session_layout.sql` — 投稿(`sessions`)がどの本部レイアウトに対応するかを保存する `layout_id` 列を追加。閲覧中の誰でも設定できるよう、`layout_id` だけを更新できる`SECURITY DEFINER`関数 `set_session_layout` も作成
- `20250101000020_truck_layouts.sql` — 納品トラック(便)とゴンドラ(売場 = `layouts`)の多対多の対応表 `truck_layouts` を追加。1つの便が複数のゴンドラに商品を持ってくるケース(例: ヤマザキパン1便 → 菓子パン・惣菜パン・マルチパン)に対応するため
- `20250101000021_image_thumbnails.sql` — 一覧表示用の軽いサムネイルのパスを持つ `thumb_path` 列を `images` / `layout_reference_photos` / `layout_current_photos` に追加。あわせてフィードのページング用に `sessions(created_at desc)`、未読バッジ計算用に `sessions(facilitator_id)` の索引を追加
- `20250101000022_feed_session_ids.sql` — フィードの絞り込み・並び替え・ページングをまとめて行う関数 `feed_session_ids` を追加。表示すべき投稿のIDだけを1ページ分返す

### 3. 認証方式の確認

メール配信の設定が不要な**匿名ログイン**(名前を入力するだけ)を採用しています。Supabase Dashboard > Authentication > Sign In / Providers で **Anonymous Sign-Ins** を有効にしてください(デフォルトは無効です)。

### 4. 環境変数

```bash
cp .env.example .env.local
```

`.env.local` に Supabase の URL と anon key を設定します。

### 5. (任意)Web Push通知を有効にする

新しい売場写真の投稿・自分の投稿へのコメントをプッシュ通知で受け取れる機能です。設定しなくてもアプリ本体は問題なく動作します。

1. VAPID鍵ペアを生成: `npx web-push generate-vapid-keys`
2. `.env.local`(と Vercel の環境変数)に追加:
   - `NEXT_PUBLIC_VAPID_PUBLIC_KEY` — 生成した Public Key
   - `VAPID_PRIVATE_KEY` — 生成した Private Key
   - `SUPABASE_SERVICE_ROLE_KEY` — Supabase Dashboard > Project Settings > API の `service_role` シークレット(RLSを無視して通知購読を検索するために使用。**サーバー専用の秘密情報なので `NEXT_PUBLIC_` を付けないこと**)
3. `20250101000011_push_subscriptions.sql` を適用

通知が届くのは **iOS 16.4以降でホーム画面に追加したPWA** または対応するAndroid/デスクトップブラウザのみです(iOS 16.4未満の端末では通知機能自体が表示されません)。

### 6. 開発サーバー起動

```bash
npm install

```

[http://localhost:3000](http://localhost:3000) を開きます。

プロフィールシートの「🔔 通知を有効にする」から、新しい売場写真の投稿・自分の投稿へのコメントをWeb Pushで受け取れます(対応端末のみボタンが表示されます)。通知の送信は `src/app/api/notify/route.ts` が担当し、`src/lib/supabase/admin.ts` の service role クライアントで購読者を検索して `web-push` パッケージで配信します。

タグ編集シート(`tag-manager-modal.tsx`)は独立したブラウザ標準の`<dialog>`要素(`showModal()`)として実装しており、背景のタップ・フォーカスはブラウザ自身に無効化させ、`body-scroll-lock`パッケージ(`src/lib/use-body-scroll-lock.ts`)で背景のタッチスクロールも止めています(iOS Safariでは`<dialog>`だけでは背景スクロールが止まらないことがあるため)。`createPortal`で`document.body`直下に描画しており、ネストした親要素によるクリッピングも受けません。

以前はコメント一覧をまとめて見るための専用モーダル(`session-comment-modal.tsx` → `pin-board.tsx`)がありましたが、💬アイコンをタップしても正しく開かないという報告があり(インストール済みPWAとSafariの双方で発生し、原因の特定には至りませんでした)、そもそもフィード写真に直接タップしてコメントできるため画面遷移自体が不要と判断し、両ファイルごと削除しました。💬アイコンは件数表示のみの`<span>`になっています。

データの読み込み・書き込みが発生するすべての箇所で `src/components/loading-overlay.tsx` を表示し、アプリの使い方やアイコンの意味をランダムなヒントとして案内します。ページ遷移(`src/app/loading.tsx`によるルート全体のSuspenseフォールバック)、複数枚アップロード、対応済み写真の登録、新商品導入の売場写真一覧の読み込み、本部レイアウト比較のピン読み込みなど。フィードのコメント用タグ候補のような補助的なバックグラウンド取得は、画面全体をブロックしたくないためオーバーレイの対象外にしています。

## データモデル

`sessions`(1枚の画像を囲むブレスト会) → `images`(売場画像、Storageパスと店舗/棚カテゴリのメタ情報) → `comments`(相対座標0〜1のピン位置 + good/bad種別 + 本文 + 投稿者)。`reactions` はセッション単位で1ユーザー1件(`unique(session_id, user_id)`)の「完成(done)/まだまだ(needs_work)」を保持し、フィードの完成率計算に使う。`claps` は1人が何回でも送れる「ありがとう」の応援ログで、投稿したスタッフのモチベーション向上が目的のため上限や1人1票制限はない。

`images.embedding` はフェーズ2以降の類似画像検索用に予約したカラムで、MVPでは未使用です。`push_subscriptions` はWeb Push通知の購読情報(ブラウザから発行されるendpoint/鍵)を保持し、通知送信時にservice roleキーで参照します。`tags` はコメント種別(good/bad)ごとの「よく使う文言」で、投稿されるたびに自動で蓄積(既存タグは`use_count`を加算、未登録の文言は新規追加)されるほか、コメント入力画面から手動で追加・編集・削除もできます。

本部レイアウト比較機能(`/layouts`)は上記の意見出しモードとは独立したデータモデルです。`layouts`(売場の名前、約50件)→ `layout_reference_photos`(本部お手本写真。季節・年ごとに追加され、最新のものが現行レイアウトとして扱われる)、`layouts` → `layout_current_photos`(店舗ごとの現在の売場写真)、`layouts` → `layout_tasks`(店舗ごとの対応タスク。`done`/`done_at`でチェックリストとして管理)という構造です。写真は既存の`shelf-images`ストレージバケットを再利用しています。`pins`は`layout_reference_photo_id`/`layout_current_photo_id`のどちらか一方(CHECK制約で排他)に紐づく汎用コメントピンで、`src/components/photo-annotator.tsx`が描画とタップ配置を担当します。

### 移動・フェイス拡げる・フェイス縮めるのオブジェクトピン(始点→終点の線描画)

「このフェイスを拡げる」のような当たり前の指示まで毎回文章で打つのは手間なので、`object_kind`(`move` / `widen` / `narrow`)を設定すると、文章の代わりに矢印の線だけを貼り付けられます。当初は1点タップ+小さいアイコンで表現していましたが視認性が悪かったため、**画像上をドラッグして始点→終点を指定し、離した後にどのオブジェクトを配置するか選ぶ**方式に再設計しました(`src/components/pin-object-line.tsx`)。

- 画像を**タップ**(ほぼ動かさず指を離す)すると、従来どおり文章コメント用のピンが開きます。
- 画像を**ドラッグ**(約10px以上動かして指を離す)すると、そのドラッグの始点・終点を結ぶ線のプレビューが表示され、離した時点で「移動 / フェイス拡げる / フェイス縮める」の3択が現れます。選ぶとテキストなしでその場に投稿されます。
- 描画される矢印は`object_kind`によって向きが変わります。「移動」は終点方向への矢印1本、「フェイス拡げる」は始点・終点の両方から外向き(互いに離れる向き)の矢印、「フェイス縮める」は両方から内向き(互いに近づく向き)の矢印です。
- 線の中央には文章ピンと同じ流れるコメント(marquee)で「移動」「フェイス拡げる」「フェイス縮める」というラベルが自動で表示されます(手入力不要。オブジェクト選択時に自動で決まります)。
- 終点座標(`end_position_x`/`end_position_y`)を持つピンだけがオブジェクトとして描画され、`object_kind`が`null`のピンは従来どおり`PinChip`が文章として描き分けます。この再設計より前に作られた、終点を持たない旧オブジェクトピン(1点タップ+アイコン方式)は、始点しか無いため描画されなくなります。
- 本部レイアウト比較・新商品導入の`pins`テーブルだけでなく、日々の投稿(フィード)の`comments`テーブルにも同じ`object_kind`・終点カラムがあり、`photo-annotator.tsx`と`comment-pin-board.tsx`の両方が同じドラッグ操作を提供します。
- ドラッグ検出を実装した際、画像に`touch-action: none`を指定していたためフィードで写真の上を指でなぞってスクロールしようとした操作までドラッグとして誤検出され、誤タッチ(意図しないピン/オブジェクトの作成)が増える不具合がありました。`touch-action: pan-y`に変更し、縦方向のスワイプはブラウザのネイティブスクロールに任せ、横方向・斜め方向の動きだけをオブジェクト線のドラッグとして検出するように修正しました。ブラウザがジェスチャーをスクロールとして奪った場合(`pointercancel`)は何も作成せずに中断します。
- フィードでオブジェクトを配置しようとすると`comments_height_pct_range`のCHECK制約違反で投稿に失敗する不具合がありました。`comments`テーブルは`width_pct`/`height_pct`に`0 < 値 <= 1`という制約があるため(`pins`テーブルにはこの制約が無く、本部レイアウト比較・新商品導入側では問題になりませんでした)、オブジェクト用の未使用プレースホルダーとして送っていた`0`が弾かれていました。`comment-pin-board.tsx`の`submitLineObject`でデフォルトの枠サイズ(`BASE_WIDTH_PCT`/`BASE_HEIGHT_PCT`)を代わりに送るよう修正しました(値自体はオブジェクトの描画に使われないので何でも構いませんが、制約を満たす必要があります)。
- `touch-action: pan-y`の都合上、ドラッグの最初の一瞬が真上/真下方向だとブラウザ側のスクロールとして扱われてしまいます。ほぼ縦の矢印を引きたい場合は、最初に少しだけ斜め/横方向に動かしてからドラッグ先を縦方向に動かすと描画できます(一度ドラッグ操作だと判定されれば、その後はどの方向に動かしても構いません)。

### 文章コメントピンの枠を縦横自由にリサイズ

文章コメントピン(`PinChip`で描画される、流れるコメントを表示する枠)は、投稿前のプレビュー右下の◯ハンドルをドラッグしてサイズ変更できます。以前は中心からの距離だけで縦横同じ倍率に拡縮していましたが、「最も自由に大きさを変えられるといい」という要望を受けて、ドラッグの水平方向の移動量で幅を、垂直方向の移動量で高さを、それぞれ独立に決められるように変更しました。角度スライダーで枠を回転させている場合は、ドラッグの座標を回転角度分だけ逆回転してから幅・高さを計算しています(`photo-annotator.tsx`の`handleResizeStart`、`comment-pin-board.tsx`の`handleResizeStart`)。

### 店舗・納品トラックのマスタ管理

以前は店舗リスト(`src/lib/stores.ts`)と納品トラック(便)リスト(`sessions/new/page.tsx`内の`SHELF_CATEGORIES`)がソースコードに直書きされていましたが、`stores`/`delivery_trucks`テーブルに置き換え、`/masters`から追加・編集・削除できるようにしました。`/sessions/new`・`/layouts`・`/new-products`はいずれもこの2テーブルをサーバー側で取得してから画面を組み立てます。`images.shelf_category`列は元は売場カテゴリ用でしたが、運用実態が納品トラック単位だったため、列名はそのままに納品トラック名を保存する形に読み替えています。

### フィードのプルリフレッシュ

フィードは`reactions`/`claps`/`comments`/`tags`のINSERT等をRealtimeで購読していますが、新しい投稿(`sessions`テーブル)自体は購読しておらず、これまでは他の人の新規投稿を見るには手動でページを再読み込みするしかありませんでした。`src/components/pull-to-refresh.tsx`を追加し、フィードを一番上までスクロールした状態で下にドラッグすると、投稿一覧・リアクション・ありがとう数・コメント・投稿者名をまとめて再取得するようにしました。

実装はスマホの一般的なプルリフレッシュと同様に、ページ最上部(`window.scrollY === 0`)でのポインタードラッグ量に応じてインジケーターの高さを伸ばし、一定量(64px)を超えて指を離すとスピナー表示に切り替えて再取得します。この用途では通常のスクロールを妨げないよう`touch-action`はあえて指定せず、実際に下方向へのドラッグを検知できた時だけ`preventDefault()`してブラウザのバウンス(引っ張り時の伸縮アニメーション)と競合しないようにしています。データ取得が一瞬で終わるとスピナーがほぼ一瞬しか表示されず更新されたか分かりにくいため、`Promise.all`で実際の取得と最低表示時間(600ms)の両方を待ってからスピナーを消すようにしています。あわせて、投稿ごとのコメント件数(💬の数字)もページ初回読み込み時の静的な値ではなく、常に最新の`comments`配列から算出するように変更したため、プルリフレッシュ後だけでなく他の人の新規コメントでも件数がリアルタイムで更新されます。

### フィード投稿に本部レイアウト(売場)を紐付ける

共有ボタンをA4フィードバックシート画像の書き出しに変更する準備として、フィード投稿(`sessions`)がどの本部レイアウト(`/layouts`で管理している約50の売場)に対応するかを紐付けられるようにしました。投稿は店舗+納品トラック単位、本部レイアウトは売場単位と管理の粒度が違うため自動では対応付けられず、また投稿時に選択を必須にすると一手間増えて負担になるため、**投稿後に閲覧中の誰でも後から設定できる**方式にしています。

フィードカードの店舗名/納品トラック表示の隣に「🏬 売場を選択」という控えめなセレクトを配置し(未設定は破線の枠、設定済みは選んだレイアウト名を表示する青い枠になる)、選択すると`set_session_layout(p_session_id, p_layout_id)`という`SECURITY DEFINER`のPostgres関数を呼んで`sessions.layout_id`を更新します。`sessions`への直接UPDATEは司会者本人のみに制限されたRLSポリシー(`20250101000003_rls_policies.sql`)のままにしつつ、この関数は`layout_id`列だけしか触らないため、権限を緩めずに「閲覧中の誰でも売場を選べる」を安全に実現しています。

選んでもらうこと自体が地味な手間なので、選択した瞬間に画面いっぱいに紙吹雪・花火・「ご協力ありがとうございます」の流れるバナーが数秒流れるお礼演出(`src/components/thank-you-celebration.tsx`)を追加しました。未選択に戻す操作(プルダウンで「🏬 売場を選択」を選び直す)では演出は出しません。

この`layout_id`は下記のフィードバックシート機能で、投稿写真と並べて本部お手本写真を自動表示するために使います。

### 共有ボタン→A4フィードバックシート画像の生成

📤共有ボタンは、以前はセッションへのリンクを共有するだけでしたが、印刷して掲示したり店舗に直接渡したりできるよう、**A4サイズ(1240×1754px, 150dpi相当)のフィードバックシート画像(PNG)をその場で生成して共有**するように変更しました(`src/lib/feedback-sheet.ts`の`generateFeedbackSheetBlob`、Canvas APIで直接描画)。

- 上段: 店舗名・納品トラック・アプリ名・投稿日・投稿者・投稿タイトル
- 写真: 投稿に本部レイアウトが紐付いている場合(前述の「売場を選択」)は、そのレイアウトの最新お手本写真(彩度を落として参考写真だと分かるようにする)と投稿写真を並べて比較表示。紐付いていない場合は投稿写真だけを大きく表示
- 投稿写真の上には、文章ピンをアプリ画面と同じ枠+テキスト(`PinChip`相当、回転にも対応。枠に収まらない場合はフォントを縮小し、それでも収まらなければ末尾を「…」で省略)、オブジェクトピン(移動/フェイス拡げる/縮める)を同じく矢印で描画(`PinObjectLine`と同じ計算式をCanvas用に書き直したもの)
- 番号バッジに対応する文章コメントの全文一覧(✅/⚠️で色分け。写真上の枠で省略された分もここで読める)。A4の決まった高さに収まる件数だけ表示し、入り切らない分は「ほかN件はアプリでご確認ください」という注記に切り替える(コメントが多い投稿でもシートからはみ出さない)
- 下段: 🙏ありがとう・✅完成・🔧まだまだの件数と完成率、書き出し日時とURL

写真は`object-fit: cover`(トリミングして枠を埋める)ではなく`object-fit: contain`相当(トリミングせず全体を収める)で描画しています。ピンの座標は投稿時点の元画像に対する相対位置で保存されているため、写真をトリミングして描画すると見えている範囲とピン座標がずれ、実機での確認で矢印が実際の位置からずれたり短くなったりする不具合がありました。containで実際に描画された矩形を基準にピン・矢印を配置することで解消しています(投稿写真自体の縦横比に合わせて描画領域の高さも決めるため、極端な縦長/横長でない限り余白は生まれません)。

生成した画像は`navigator.canShare({ files })`に対応していれば`navigator.share`で画像ファイルとして共有(LINEなど)、対応していない端末ではダウンロードにフォールバックします。投稿写真・お手本写真はSupabase Storageの公開URLから`crossOrigin="anonymous"`で読み込んでCanvasに描画するため、ストレージ側のCORS設定次第では読み込みに失敗する可能性があります(この環境では実機確認ができていないため、生成に失敗する場合は教えてください)。

このアプリは`supabase.auth.signInAnonymously()`による匿名ログイン+自己申告の表示名(`profiles.display_name`)という認証方式のため、同じ人でも再ログインするたびに別の`user_id`(別のauth.usersの行)になります。「✅完成/🔧まだまだ」の1人1票判定は`reactions`テーブルの`unique(session_id, user_id)`制約に依存していたため、再ログイン後は別のuser_idとして扱われ、同じ人が何度でも投票し直せてしまう不具合がありました。

`user_id`ではなく`profiles.display_name`が一致するかどうかで「既に投票済みか」を判定するように`feed.tsx`の`handleReact`と描画ロジックを変更しました。既存の投票が自分の今のuser_idに紐づいている場合は従来どおり押し直して変更・取り消しができますが、表示名は同じでも別のuser_id(=別のログイン)に紐づく投票が見つかった場合は、ボタン自体を`disabled`にして押せないようにしています。`reactions`テーブルの更新・削除RLSポリシーが`auth.uid() = user_id`を要求するため、他人(別user_id)の投票行をこちらから書き換えることはできず、ボタンを無効化する以外の対処はできません。同じ表示名を複数人が名乗った場合は区別できない点は変わらないため、表示名は他の人と被らないようにしてください。

### フィード写真とモーダルのピン座標を統一した経緯

以前はフィードカードの写真を`aspect-square`+`object-cover`で正方形にトリミング表示していましたが、ピンの`position_x`/`position_y`は元画像に対する相対位置で保存されるため、専用モーダル(トリミングなし)とフィード(トリミングあり)で見える範囲がずれ、同じピンでも表示位置が食い違うことがありました。現在はフィード写真もトリミングなしの元画像を`comment-pin-board.tsx`で表示するため、この問題は起きません。フィード写真は直接タップしてピンを配置できます(300ms以内の連続タップは従来どおり「ありがとう」のダブルタップ判定を優先)。`session-card.tsx`は`comment-pin-board.tsx`の見た目・操作ロジックと`src/lib/submit-comment.ts`の投稿処理(タグ使用回数の更新・通知送信を含む)を利用しています。

### ゴンドラ(売場)ごとの撮影 — 1便が複数のゴンドラに並ぶケース

納品トラック(便)とゴンドラ(売場)は1対1ではありません。たとえばヤマザキパン1便は菓子パン・惣菜パン・マルチパンの3つのゴンドラに商品を持ってくるため、1便につき3枚の写真が必要です。従来のウィザードは「店舗→便→カメラ」で終わっていたため、どの写真がどのゴンドラのものかは後から誰かが手作業で紐付けるしかありませんでした。

そこで便とゴンドラの対応表(`truck_layouts`)を追加し、ウィザードに**ゴンドラ選択のステップ**を挟みました。

- ゴンドラのマスタは本部レイアウト比較の`layouts`テーブルをそのまま使います(同じ「◯◯売場」を二重管理しないため)。UI上の呼び名だけ「ゴンドラ」に統一しました。
- どの便がどのゴンドラを持つかは`/masters`の「納品トラックとゴンドラの紐づけ」で設定します。便ごとにゴンドラをタップして選ぶだけで、`truck_layouts`に行が追加・削除されます。
- **紐づけ済みの便では、スタッフにゴンドラを選ばせません。** 便を選んだ時点で撮る順番が確定するので、「① 菓子パンを撮影してください」→撮る→「② 惣菜パン」→…と1つずつ案内し、最後まで行くと完了画面になります。選択肢を並べると現場で「どれを撮ればいいのか」と迷う一方、便とゴンドラの対応は事前に決まっているため、そこはアプリが持つべき知識だと判断しました。
- 撮影ガイドには、そのゴンドラの**最新の本部お手本写真**と「このあとのゴンドラ」の残り一覧を出します。撮る前に正解の売場が見えるので、何を撮ればいいか・あと何件かが同じ画面で分かります。お手本写真が未登録のゴンドラではその旨だけ表示し、撮影自体は進められます。
- 逃げ道として「このゴンドラは飛ばす」「一覧から選んで撮る」を用意しています。後者を押すと下記の一覧モードに切り替わります。
- 紐づけがまだ無い便や「その他」で手入力した便は撮る順番を決めようがないため、従来どおり**一覧から選ぶモード**になります。こちらは撮影のたびに戻ってくるハブで、撮り終えたゴンドラには✅と枚数が付きます。「ゴンドラを指定せずに撮影する」も残しています。
- 撮影時にゴンドラが分かるので、作成されるセッションには`layout_id`が最初から入ります。これにより、後から誰かに紐付けてもらう手間(前述の「🏬 売場を選択」)は基本的に不要になりました。過去の投稿のために、カード上のセレクトは従来どおり残してあります。

### 日本語 / English / नेपाली の切り替え

外国人スタッフも使うため、表示言語をプロフィールシートから3言語で切り替えられるようにしました(`src/components/language-switcher.tsx`)。

- 文言は`src/lib/i18n/dictionaries/`に言語ごとのオブジェクトとして持ちます。日本語(`ja.ts`)が原本で、その型(`Dictionary`)に`en.ts`・`ne.ts`が従うため、**キーを足し忘れるとコンパイルエラーになります**。件数や名前を埋め込む文言は文字列ではなく関数(例: `thanks: (count) => ...`)にしており、語順が言語ごとに違っても対応できます。
- 選択した言語はURLではなく**Cookie**(`locale`)に保存します。`/[lang]`のようなパス分割にすると、プッシュ通知や共有リンク(`/?session=...`)のURLが言語ごとに変わってしまうためです。クライアントは`I18nProvider`のコンテキストから、サーバーコンポーネントは`src/lib/i18n/server.ts`の`getDictionary()`からCookieを読みます。切り替え時は`router.refresh()`でサーバー側の文言も描き直します。
- A4フィードバックシート(`feedback-sheet.ts`)の見出しも同じ辞書を使うため、書き出した画像もアプリと同じ言語になります。
- Webフォントは使わず、端末に入っているフォント(日本語・デーヴァナーガリー)だけで描画します。低スペック端末で余計なダウンロードとレンダリング待ちを増やさないためです。
- 未対応: Web Push通知の本文(`src/app/api/notify/route.ts`)は送信先の言語が分からないため日本語のままです。対応するには`profiles`に言語列を追加する必要があります。

### 低スペック端末向けの軽量化

古い・安価なAndroid端末でもフィードが引っかからずに動くよう、重い順に手を入れました。

- **フィードのページング**: 以前は全投稿・全コメント・全リアクション・全ありがとうを一度に取得してから、ブラウザ側で絞り込みと並び替えをしていたため、投稿が増えるほど初回表示が重くなっていました。`feed_session_ids`というPostgres関数に「条件・並び順・何件目から何件」をまとめて任せ、返ってきたIDに紐づくデータだけを取るようにしました(`src/lib/feed-data.ts`)。1ページ8件で、下の「もっと見る」で追加読み込みします。店舗・納品トラック・ゴンドラの絞り込みと並び替えもこの関数側で行うため、読み込み済みの範囲だけが対象になることはありません。
- **サムネイル**: アップロード時に原寸(最大1600px)に加えて一覧用の軽い画像(最大960px)も作り、`thumb_path`に保存します(`src/lib/image.ts`・`src/lib/upload-image.ts`)。一覧・フィードはサムネイル、フィードバックシートの生成は原寸を使います。JPEGのデコードは低スペック端末でいちばん重い処理なので、デコード面積がおよそ1/3になる効果は大きいです。サムネイル導入前の写真は`thumb_path`が空なので、自動的に原寸へフォールバックします。
- **画面外カードの描画スキップ**: 投稿カードに`content-visibility: auto`(`.card-defer`)を付け、画面外にあるあいだはレンダリングを省きます。あわせて画像を`loading="lazy"` / `decoding="async"`にしています。
- **再描画の削減**: `SessionCard`を`memo`化し、コメント・リアクションは投稿ごとの`Map`に一度だけ振り分けます(以前はカードごとに全件を`filter`していたため投稿数×コメント数の計算になっていました)。コールバックも`useCallback`で固定しています。
- **ドラッグ処理の間引き**: ピンの移動・リサイズ・オブジェクト線のドラッグは`pointermove`のたびに状態を更新していましたが、`src/lib/raf-throttle.ts`で1描画フレームにつき1回に間引きました。
- **Supabaseクライアントの使い回し**: `createClient()`は呼ぶたびに認証・Realtimeの状態を持つ新しいインスタンスを作ります。以前はコンポーネントの描画のたびに呼んでいたため無駄が積み上がっていたので、アプリ全体で1つを使い回すようにしました。
- **Realtime購読の統合**: フィードで2つに分かれていたチャンネルを1つにまとめ、読み込んでいない投稿のイベントは無視します。
- **初回バンドルの削減**: Webフォント(Geist)の読み込みをやめて端末のフォントに切り替え、A4シート生成(`feedback-sheet.ts`)・お礼演出・タグ編集シートは使う瞬間まで読み込まないようにしました(`next/dynamic`と動的`import()`)。

### 軽量化・ゴンドラ導線のあとに見つかった不具合と対処

ページング・サムネイル・撮影ガイドを入れたあとにコードレビューで洗い出したもの。いずれも「動くが壊れている」種類で、テストでは気づきにくいものです。

- **アップロードされた写真が真っ白になりうる**(`src/lib/image.ts`) — 原寸とサムネイルを1回のデコードで作るようにした際、`blob:` URLを画像の読み込み直後に解放していました。WebKitでは描画元が無効になり空のcanvasになることがあり、縮小後は元より軽いのでサイズ判定も通ってアップロードされてしまいます。両方を描き終えてから解放するよう直しました。
- **`/?session=<id>` のリンクが開かなくなっていた**(`src/app/(protected)/feed.tsx`) — フィードが8件ずつになったため、コメント一覧やプッシュ通知から古い投稿を開いてもDOMに無く、スクロールが無言で失敗していました。読み込み済みに無い場合はその1件だけ取得して先頭に差し込みます(`fetchSessionWithRelations`)。
- **「もっと見る」で同じ投稿が二重に出る** — オフセットは件数なので、閲覧中に新しい投稿が入ると次のページに同じ投稿が現れ、リアクションも二重計上されていました。IDで重複を弾いています。
- **全画面オーバーレイがカード内に閉じ込められる** — `content-visibility: auto` は paint containment を伴うため、カード内に置いた `position: fixed` の基準がカード自身になります。オーバーレイをカードの外に出しました。
- **絞り込みの候補と実際の値がずれる** — 候補をマスタから作ると、「その他」で手入力した便は選べず、マスタの名前を変えると古い投稿が出てきません(実際に本番には `テスト` という手入力の店舗・便が存在していました)。実データの値を返す `feed_filter_options()` から候補を作るようにしています。
- **素早いドラッグがタップとして誤判定される** — `pointermove` を1フレーム1回に間引いた際、指を離すときに保留中の呼び出しを捨てていました。1フレーム内で終わる操作は「動いていない」と判定され、矢印ではなく文章コメントの入力欄が開きます。離すときは捨てずに実行(`flush`)します。
- **紐づけを続けてタップすると1つ消える**(`masters-editor.tsx`) — `await` を挟んで更新前の配列を書き戻していたため、後の更新が前を巻き戻していました。更新関数で最新の値から作り直します。
- **撮影ガイドの順番が不定**(`sessions/new/page.tsx`) — `truck_layouts.sort_order` に値を入れるUIが無く全行0だったため、並び順が取得のたびに変わりえました。ゴンドラのマスタ順(一覧画面と同じ並び)に揃えています。
- **全部飛ばしても「すべて撮り終えました」と出る** — 1枚も撮っていない場合は別の文言にし、撮っていないゴンドラを一覧で出してその場から撮り直せるようにしました。
- **通信エラーで「もっと見る」が消えたまま戻らない** — 取得失敗時に `hasMore` を false にしていたため。成功時だけ更新します。

未対応として残したもの: `layout_reference_photos` の取得に絞り込みも上限も無く、投稿ウィザードを開くたびに全件を並べ替えています。現状このテーブルはごく小さい(ゴンドラごとに数件)ため実害が無く、件数が増えてきたら `layout_id` ごとの最新1件を返す形に変える想定です。

### 写真の拡大表示

値札が読めない・フェイス数が数えられない、という声から、写真を全画面で拡大して見られるようにしました(`src/components/photo-viewer.tsx`)。

設計上いちばん効いた制約は、**フィード写真のタップ操作がすでに全部埋まっている**ことです。タップ=コメントピン、ダブルタップ=🙏、ドラッグ=矢印オブジェクト。ここに「タップで拡大」を足すと主要な操作が壊れます。そこで拡大は写真上ではなく専用のビューアに分け、🔍ボタン(および改善前/改善後のサムネイルのタップ)で開く形にしました。ビューアの中では操作が競合しないので、ダブルタップを段階拡大に割り当てられます。

- ビューアが表示するのは**一覧用サムネイル(960px)ではなく原寸(1600px)**です。フィードはサムネイルのままなので軽さは変わらず、見たいときだけ解像度を取りに行きます。その場で拡大しても粗くなるだけ、という状況を避けるのが目的です。
- ダブルタップで 1倍 → 2倍 → 4倍 → 等倍 と切り替わります。店内では片手が塞がっていることが多いため、ピンチだけに頼らず片手で拡大できるようにしています。2本指のピンチでも無段階に拡大できます(アプリ全体で `user-scalable=no` にしてブラウザのズームを切っているため、ピンチは自前実装です)。
- 拡大するとピンが写真を隠すので、表示/非表示のトグルを置いています。
- 写真は中央ぞろえで表示し、`transform` の移動量は「中央からのずれ」として扱います。拡大して画面からはみ出した分の半分までしか動かせないよう制限しているので、写真が画面の外へ逃げません。
- ビューアは `createPortal` で `document.body` 直下に描画します。投稿カードは `content-visibility` で paint containment が効いており、その中に置くと `position: fixed` がカード内に閉じ込められるためです(同じ理由でローディングオーバーレイもカードの外に出しています)。
- フィード・本部レイアウト比較・新商品導入の3箇所から同じコンポーネントを呼びます。左右に並べて比較する本部レイアウト比較は半分幅で表示されるぶん、実は拡大の必要性が一番高い画面です。

`max-height: 100%` は親の高さが自動だと効かないことがあるため、表示領域の実寸を `ResizeObserver` で測ってpxで指定しています。

見送った案: カード上でそのままピンチ拡大する案は、ジェスチャーの衝突こそ無いものの、サムネイルを拡大しても粗いだけで、原寸に差し替えるとスクロール中に重くなり軽量化の効果を打ち消します。長押しで拡大する案は隠し機能になって現場で気づかれず、ドラッグ判定とも紛らわしいため見送りました。

### 拡大したままピンを打つ

上のビューアは「見る」専用なので、小さい商品に正確にピンを置きたいという用途には別の仕組みを足しました(`src/lib/use-photo-zoom.ts`)。写真の枠の中で拡大し、拡大したままタップしてピンを置けます。

- **拡大と移動は2本指**に割り当てています。1本指はピン(タップ)・矢印(ドラッグ)・ページの縦スクロールにすでに使われているためで、写真アプリや地図と同じ感覚のまま、片手の操作を一切奪いません。つまみながら指を動かせば拡大と移動が同時にできます。
- **座標変換のコードは要りません。** ピンの位置は `imageRef.getBoundingClientRect()` を基準にした0〜1の相対値で計算しており、`getBoundingClientRect()` は CSS transform を反映した矩形を返します。そのため写真を包む外側の要素に `scale()` を掛けるだけで、「指が触れた場所 = 写真上の同じ場所」が拡大中もそのまま成り立ちます。枠のサイズ計算(`width_pct × imgSize.width`)も、`ResizeObserver` の `contentRect` が transform 前のレイアウト寸法を返すので、px値はそのままで見た目だけが一緒に拡大されます。
- 2本目の指が触れた時点で、打ちかけのピン・矢印は取り消します(拡大のつもりの操作が誤ってピンにならないように)。
- 枠には `touch-action: pan-y` を指定しています。1本指の縦スクロールはブラウザに任せつつ、2本指のジェスチャーを奪われないようにするためです(奪われるとピンチの途中で `pointercancel` が飛びます)。
- 拡大中は左上に「等倍に戻す」が出ます。この解除ボタンとリアクションの表示は transform の外側に置いているので、拡大しても大きさが変わりません。

フィードのコメントピン(`comment-pin-board.tsx`)と、本部レイアウト比較・新商品導入のピン(`photo-annotator.tsx`)の両方で同じフックを使っています。

## 既知の制約

- 匿名ログインのため、一度サインアウトすると同じ名前で再ログインしても内部的には別ユーザー(別のauth uid)として扱われます。なりすまし防止や本人確認はできません(MVPのスコープ外)。
- コメントは匿名投稿です。投稿者は `author_id`(user id)として構造化データには保存されますが(将来の分析・モデレーション用)、UI上は誰が投稿したか一切表示されません(自分の投稿かどうかも含めて非表示)。活発な意見出しを促すための意図的な設計です。一方で売場写真そのものの投稿者(司会者)はフィード上に表示されます。「ありがとう」やコメントというフィードバックが誰への評価かが分かるようにするための意図的な例外です。
